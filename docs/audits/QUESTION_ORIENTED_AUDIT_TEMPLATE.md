# Вопросно-ориентированный аудит игровых логов

Версия: 0.1 (пилотная)

## Назначение

Главный отчёт должен отвечать на исследовательские вопросы, а не пересказывать
партию по ходам. Построчный ledger допустим только как проверяемое приложение.

Любой результат сначала описывается вместе с полным **treatment contract** —
условиями и поддержкой, которые получила модель. Если модель видела список
легальных ходов, движковую оценку, историю партии или специально запрошенные
поля плана, это является частью причинного условия эксперимента, а не мелкой
оговоркой в конце отчёта.

Единица вывода — не отдельная фраза модели, а связка:

1. заранее зафиксированное утверждение или намерение;
2. последующие позиции и действия;
3. объективная шахматная проверка;
4. сильнейший контрпример;
5. граница того, что лог вообще способен доказать.

## Термины

- **Provider-visible reasoning** — поле `thinking`, возвращённое API-провайдером.
  Оно может быть пересказом или сокращённым представлением и не считается
  полным скрытым chain of thought.
- **Публичное объяснение** — поля `plan`, `phase`, `progress`, `rationale`.
- **Точный прогноз** — заранее названная последовательность ходов либо
  условная ветка вида «если X, то Y».
- **Горизонт обязательства** — заранее названные будущие собственные действия
  или этапы, даже если все ответы соперника не перечислены.
- **Подтверждённый горизонт** — непрерывный префикс реально сыгранной линии,
  совпавший с прогнозом. Текущий ход в горизонт не входит.
- **WDL** — win/draw/loss из таблиц; сохранение WDL не означает оптимальность
  хода и не является числом ходов до мата.
- **Ветвистость** — число легальных ответов защитника после хода модели.

## Шкалы

### Ответимость вопроса

- `FULL` — первичный лог и механическая проверка позволяют ответить в заданной
  области.
- `PARTIAL` — ответ возможен только с оговоркой, для части выборки или через
  интерпретацию.
- `NONE` — имеющиеся данные не позволяют честно ответить.

### Результат

- `YES` — наблюдаемое поведение подтверждает проверяемое утверждение.
- `MIXED` — есть и подтверждения, и содержательный контрпример.
- `NO` — проверяемое утверждение опровергнуто в данной области.
- `NOT_TESTED` — вопрос не был реально испытан.

### Уверенность

- `HIGH` — детерминированный replay или прямое дословное свидетельство.
- `MEDIUM` — воспроизводимая интерпретация с ограниченной неоднозначностью.
- `LOW` — слабая интерпретация; не использовать как основной тезис статьи.

### Классы доказательств

- `M` — механическое: replay, legal moves, FEN, terminal state, WDL,
  ветвистость, RNG receipt.
- `L` — прямое логовое: prompt, request envelope, provider-visible reasoning,
  публичный ответ.
- `I` — интерпретация аудитора.
- `X` — внешний контроль: независимый движок, таблицы, другой аудитор.

Вывод о стратегии не может опираться только на `I`.

## Treatment contract и абляции

Перед анализом заполнить таблицу:

| Компонент | Что получила модель | Источник | Какую подзадачу снимает | Проверялся ли вариант без него |
|---|---|---|---|---|
| Представление позиции |  | harness/user |  |  |
| Сторона и цель |  | harness/user |  |  |
| Legal-move oracle |  | rules engine | Генерация и фильтрация легальных кандидатов |  |
| История партии |  | harness | Восстановление эпизодической памяти |  |
| Стратегическая инструкция |  | system prompt | Самостоятельная постановка цели/плана |  |
| Структура ответа |  | system prompt | Самостоятельный выбор формы планирования |  |
| Correction feedback |  | harness | Самостоятельное восстановление после ошибки |  |
| Инструменты/память |  | runtime |  |  |

Правило переноса вывода:

> Если компонент не был удалён в контролируемой абляции, результат относится
> только к условию с этим компонентом.

В частности, наличие полного списка legal moves позволяет заключать, что
модель выбирает и исполняет действия из корректного множества кандидатов. Оно
не позволяет заключать, что модель самостоятельно построит то же множество,
избежит нелегальных ходов или сохранит ту же эффективность без списка.
Даже без оценок и ранжирования такой список снимает генерацию кандидатов,
фильтрацию нелегальных действий и часть проверки геометрии позиции.

Модель без возможности самостоятельно вызвать tool всё равно нельзя
безоговорочно называть «без шахматной инструментальной поддержки», если
harness заранее вставляет в prompt вычисленный движком legal-move oracle.

## Gate 1: целостность и воспроизводимость

До смыслового анализа заполнить:

```text
[ ] Идентичность модели и endpoint записана.
[ ] System prompt, request parameters, request messages, raw text и
    provider-visible reasoning сохранены.
[ ] Каждый ход воспроизводится из starting FEN.
[ ] FEN до/после, SAN/UCI и terminal state совпадают.
[ ] Ходы защитника легальны; RNG receipt или правило выбора воспроизводимо.
[ ] Protocol corrections, transport retries и усечения ответа перечислены.
[ ] Первый запрос каждой партии не содержит историю другой партии.
[ ] На каждом лог-событии есть run_id, game_id/position_id, record_seq и ply.
[ ] Явно перечислено всё, что модель получила в prompt, включая legal moves.
[ ] Главный вывод повторяет существенные элементы treatment contract.
[ ] Для каждого engine-derived поля указано, какую способность оно снимает с
    модели и проводилась ли абляция.
```

Если запись можно восстановить только из порядка строк, это фиксируется как
дефект схемы, даже когда конкретный replay успешен.

## Gate 2: калибровка представления и правил

Для каждой неигровой калибровочной доски проверить не только JSON-схему, но и
семантику:

```text
Доска:
Формат:
Сторона хода:
Фигуры и клетки:
Количество фигур:
Правила движения:
Специальное состояние FEN (рокировка, en passant и т. п.):
Предпочтённый формат и feedback:
Ошибки/противоречия:
Вердикт: PASS / PASS_WITH_LIMITATION / FAIL
```

Hard fail для игрового теста:

- неверно определены активные фигуры или сторона хода;
- неверно объяснено базовое движение участвующей фигуры;
- модель сообщает, что не понимает ни один предложенный формат;
- формат игровой доски отличается от выбранного без новой калибровки.

Нерелевантная конкретной задаче ошибка специального состояния не должна
скрываться, но её влияние на валидность следует определить заранее, а не после
результата.

## Карточка исследовательского вопроса

Для каждого вопроса используется одна и та же форма:

```text
ID и вопрос:
Операциональное определение:
Область ответа:
Ответимость: FULL / PARTIAL / NONE
Результат: YES / MIXED / NO / NOT_TESTED
Уверенность: HIGH / MEDIUM / LOW
Метрика:
Сильнейшие доказательства (2–3):
Сильнейший контрпример:
Альтернативное объяснение:
Что лог не доказывает:
Следующий тест, способный опровергнуть вывод:
Evidence refs:
```

## Набор исследовательских вопросов

### A. Валидность

1. Все ли ходы легальны и воспроизводимы?
2. Правильно ли модель понимает текущие фигуры, клетки, сторону хода и правила
   на протяжении теста?
3. Что именно подтверждает отсутствие инструментов, памяти, внешней
   оркестрации, будущих ходов или иной скрытой помощи? Какие engine-derived данные harness
   уже вставил в prompt, даже если модель не могла сама вызвать tool?
4. Изолирована ли каждая партия от других партий при сохранении только истории
   текущего эпизода?

### B. Наличие стратегии

5. Формулирует ли модель позиционно-конкретный план, а не универсальный текст?
6. Разбивает ли она задачу на наблюдаемые этапы?
7. Следуют ли последующие ходы ранее заявленному плану, или план переписывается
   задним числом?
8. Делает ли модель тихие стратегические ходы, когда немедленный шах не нужен?
9. Создают ли ходы объективный прогресс: сохраняют WDL, сокращают мобильность,
   подводят короля, строят матовую сеть и избегают пата?

### C. Горизонт и ветвление

10. Какие будущие действия модель называет до их исполнения?
11. Каков максимальный и типичный подтверждённый горизонт отдельно в будущих
    полуходах и будущих собственных ходах?
12. Насколько этот горизонт обязан форсированности линии?
13. Рассматривает ли модель несколько легальных ответов защитника?
14. Адаптирует ли она существующий план после действительно неожиданного
    ответа, или начинает рассуждение заново?

Для вопроса 11 всегда приводятся две величины:

```text
Точный подтверждённый горизонт: N будущих plies / M собственных ходов.
Подтверждённый горизонт обязательства: N будущих plies / M собственных ходов.
Ветвистость на линии: [b1, b2, ...].
```

Нельзя переносить горизонт первого хода на все последующие решения.

### D. Связь объяснения и действия

15. Согласуются ли provider-visible reasoning, выбранный ход и публичные
    `plan/progress/rationale`?
16. Содержит ли reasoning проверяемые прогнозы или преимущественно общие слова?
17. Бывает ли, что модель замечает опасность, но её следующий ход нарушает
    собственное предупреждение?
18. Появляется ли описание последовательности до её исполнения, а не только
    после?

### E. Ошибки и устойчивость

19. Какие классы ошибок наблюдаются: чтение доски, геометрия атак, тактика,
    WDL, пат, потеря плана, блуждание, протокол?
20. Сохраняет ли модель критические инварианты: безопасность ферзя,
    существование легального ответа до мата, поддержка матующей фигуры,
    отсутствие повторов?
21. Повторяется ли результат на разных позициях и seed, или зависит от удачной
    случайной линии?
22. Ухудшается ли поведение при росте длины партии и ветвистости?

### F. Граница вывода для статьи

23. Отличает ли эксперимент построение новой стратегии от исполнения
    выученного алгоритма KQK?

Отдельно, без подмены ответом на вопрос 23:

```text
Что эксперимент показывает о наблюдаемом поведении:
Что эксперимент не показывает о субъективном сознании:
Что он не показывает о скрытом chain of thought:
Что он не показывает о несыгранных ветках:
Что он не показывает о других стратегических задачах:
Что он не показывает против оптимальной защиты:
```

## Формат основного отчёта

1. Полный treatment contract и область, на которую разрешён перенос.
2. Краткий вывод по центральной гипотезе именно в этих условиях.
3. Результаты Gate 1 и Gate 2.
4. Таблица из 23 вопросов:

```text
ID | Ответимость | Результат | Уверенность | Ключевое доказательство |
   | Контрпример | Ограничение | Следующий falsification test
```

5. Две-три контрастные case study, а не все ходы подряд.
6. Сильнейший контрпример к собственному выводу.
7. Какие вопросы остались без ответа.
8. Следующий эксперимент и обязательные абляции.
9. Машинный ledger ходов, WDL и ветвистости — только приложение.

## Минимальный стандарт формулировки вывода

Допустимо:

> При observation package A, engine-derived legal-move oracle B,
> стратегической инструкции C и защитнике D в данной выборке наблюдались
> заранее зафиксированные и затем исполненные многходовые обязательства;
> максимальный точный подтверждённый горизонт составил X plies / Y собственных
> ходов при ветвистости [...]. Надёжность ограничена контрпримером Z. Поведение
> без B и C не тестировалось.

Недопустимо без дополнительных данных:

> Модель сознательно думает на Y ходов вперёд.

> Модель не умеет строить стратегии вообще.

> Модель построила новую стратегию, а не воспроизвела известный шаблон.

> Модель сыграет так же эффективно без списка legal moves.
